# 五轮上下文对话：设计与使用

## 工作顺序

1. 界面在当前会话中保留最近五轮问题和各轮完整追踪。点击历史轮次，可以把原有七个标签页切换到那一轮的本体命中、Query IR、SQL 与结果。
2. 新问题提交后，`conversation.py` 只提取最近五轮的简短摘要：问题、执行状态、路由、已验证的生产计划主键和查询方向。数据库行、SQL、账号和密码不进入模型的对话上下文。
3. 本轮明确给出的计划 ID / 编号 / 名称或全局查询优先，不沿用旧主键；“再看 BOM”“改成超过 10%”等追问才沿用最近一次**执行成功且实体定位唯一**的计划 ID。阈值等旧条件不自动复制；修改分析条件时只继承上轮的分析方向。
4. 改写后的独立问题及五轮摘要传给现有 `RequestRouter`。如果模型输出的计划主键与本轮明确 ID 或可信继承 ID 不同，Pipeline 的 `selector_guard` 会强制使用可信主键，并在追踪中记录修正。
5. 后续仍走原有链路：真实实体定位 → 动态 Query IR / 注册任务 → 校验 → Semantic Mapping 编译参数化 SQL → `mom-test` 只读执行 → 可选模型结果回答。每轮 Query IR 的 `goal` 保存独立改写问题，原始提问保存在 `input.natural_language`。

## 追踪字段

- `context.original_question`：本轮用户原文。
- `context.effective_question`：本轮独立改写问题，包含允许继承的规范计划 ID 与本轮目标。
- `context.recent_turns`：最多五轮的模型可见摘要，不含 SQL 或结果行。
- `context.mode`：`NEW_QUERY`（独立查询）、`DRILL_DOWN`（同计划换查询方向）、`REFINE`（沿用方向并修改条件）、`CHANGE_SCOPE`（明确指定新计划）、`CLARIFY`（追问不完整）、`RESET`（重置）。
- `context.inherited_plan_id` / `inherited_from_turn`：可信主键及其来源轮次；没有继承时为 `null`。
- `context.explicit_source_id`：本轮明确给出的生产计划 ID；编号、名称不在这里冒充主键。
- `selector_guard`：如果模型输出定位词与可信主键不一致，记录模型值、强制值和原因。

## 可用示例

```text
第一轮：查询生产计划ID 665的详细信息
第二轮：再看对应的BOM
```

第二轮改写为“明确选择生产计划ID 665……再看对应的BOM”，然后重新生成独立 Query IR；不是修改上一轮 SQL。

```text
第一轮：分析生产计划ID 665的料差，超过5%
第二轮：改成超过10%
```

第二轮沿用“分析投料差异”的任务方向和可信计划 ID，采用本轮 10% 阈值，不把上轮 5% 重新交给模型。

明确问“生产计划ID 777”会改用新计划；问“当前有多少生产计划”不会沿用 665；问“它呢”或“换一个计划”但未说明查什么或换哪个计划，会要求补充信息。

## 当前边界

这是一版单会话、单计划 MVP。界面刷新后的 Streamlit 会话可能丢失历史；不做跨用户持久化。最近五轮用于理解问句，不代表能执行任意新查询：相对时间、多计划比较、任意字段过滤及复杂自定义公式仍受当前 Query IR、映射和编译器能力限制。DeepSeek 额度、网络或数据库不可用时，历史失败轮次不成为可继承的实体锚点。
